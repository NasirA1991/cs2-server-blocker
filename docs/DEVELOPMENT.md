# Development

This guide is for working on CS2 Server Blocker itself. For installation and
normal use, start with the [README](../README.md).

## Prerequisites

- Python 3.11 or newer.
- nftables, plus `iptables` and `ipset` for the fallback integration test.
- GTK4, libadwaita 1.5+, PyGObject and `python-cairo` for the GUI.
- `git`, a C compiler toolchain and `base-devel`/`build-essential` only if you
  build packages locally.
- `xvfb` for a headless GUI smoke test.
- `appstreamcli` for AppStream validation.
- Optional: `shellcheck`, `xgettext` and `msgfmt` for shell/i18n checks.

The project has no Python package manager lockfile and no third-party Python
runtime dependencies beyond PyGObject and Cairo.

## Checkout and run

```bash
git clone https://github.com/NasirA1991/cs2-server-blocker.git
cd cs2-server-blocker

./cs2blocker-gui --smoke-test   # construct and show the window, then exit
./cs2blocker-gui                # normal GUI from the checkout
./cs2blockctl list              # CLI from the checkout
```

A checkout can use the development launchers. Privileged commands require an
installed helper (`sudo ./packaging/install.sh`) or an explicit root invocation;
the CLI prints the exact fallback if the helper is not installed.

## Tests

Run the unit and integration suite:

```bash
make test
```

This runs `python3 -m unittest discover -s tests -v`. GUI construction is
covered when a display is available; CI runs the GUI smoke test separately in
an Arch container.

Run the isolated firewall test:

```bash
make test-netns
# equivalent:
./scripts/netns-integration.sh
```

The script re-executes itself in an isolated network namespace with
`unshare -rn`, creates `inet cs2blocker` and an unrelated test table, and
verifies apply, re-apply, pause, resume, clear and preservation of the
unrelated table. It never touches the host firewall. When `ipset` is missing,
the nftables path runs and the iptables path is skipped with a clear message.
CI runs both paths in a privileged Arch container.

Useful individual checks:

```bash
python3 -m compileall -q cs2blocker tests
python3 -m unittest tests.test_backends -v
appstreamcli validate --no-net packaging/org.cs2blocker.Gui.metainfo.xml
git diff --check
```

The tests use mocked firewall commands for the unit suite. Do not run a test
that needs root without understanding the namespace/temporary-root setup.

`cs2blocker/gui/map_data.py` is generated by `scripts/build_map_data.py` from
Natural Earth 1:110m data. The checked-in geometry is used at runtime; normal
development does not need network access or a GIS dependency. Regenerate it
only when intentionally updating the map data, and keep the Natural Earth
public-domain attribution.

## Versioning and release process

The version is single-sourced from `cs2blocker/__init__.py`. A release changes
all of these together:

- `cs2blocker/__init__.py` `__version__`
- `packaging/PKGBUILD` and `packaging/aur/PKGBUILD` `pkgver`
- `packaging/nfpm.yaml` `version`
- AppStream release entry
- README, man page and SECURITY version references where applicable

Then:

1. Run `make test`, `make test-netns`, the GUI smoke test and
   `git diff --check`.
2. Commit and push `master`; wait for CI (tests, GUI smoke, netns, package
   builds) to pass.
3. Create an annotated tag matching the version and push it:

   ```bash
   git tag -a vX.Y.Z -m "Release vX.Y.Z"
   git push origin vX.Y.Z
   ```
4. The `release.yml` workflow rebuilds the `.deb`, `.rpm`, Arch package and
   tarball, generates an SPDX JSON SBOM, signs `SHA256SUMS` with keyless cosign,
   and publishes the GitHub release.
5. The `aur.yml` workflow updates the AUR package from the same tag.

Do not build release packages on a development machine. CI is the source of
published artifacts; local package builds are only for testing the packaging
scripts.

### Verify a published release

Download the assets from the release page, then check the checksums and the
keyless signature from this repository's release workflow:

```bash
sha256sum -c SHA256SUMS
cosign verify-blob \
  --certificate SHA256SUMS.pem \
  --signature SHA256SUMS.sig \
  --certificate-identity-regexp 'https://github.com/NasirA1991/cs2-server-blocker/.github/workflows/release.yml@refs/tags/v.*' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  SHA256SUMS
```

The SPDX JSON (`cs2blocker-<version>.spdx.json`) is the SBOM. The AUR package is
published from the same tag by `aur.yml`; do not hand-edit AUR files for a
release unless the workflow failed and the maintainer has decided to recover
manually.

## Documentation

- `README.md` is the primary entry point and should stay short enough to scan.
- Detailed instructions belong in `docs/INSTALLATION.md`, `docs/USAGE.md`,
  `docs/CLI.md`, `docs/FIREWALL.md` and `docs/TROUBLESHOOTING.md`.
- Non-systemd startup and scheduling belongs in `docs/NON_SYSTEMD.md`.
- `docs/design.md` is the technical reference; update it when the architecture,
  privilege model, rule format or file layout changes.
- `docs/phase0-research.md` is a historical research record. Do not rewrite it
  as current user documentation; add a status note instead.
- Keep commands copy-pasteable and verify them against the implementation.
- Use GitHub-flavored Markdown, fenced code blocks with language identifiers,
  and relative links inside the repository.

Regenerate the translation template after changing user-facing strings:

```bash
xgettext --language=Python --from-code=UTF-8 \
  --keyword=_ --keyword=ngettext:1,2 \
  --output=cs2blocker/locale/cs2blocker.pot \
  $(find cs2blocker -name '*.py' -print)
```

The POT is an extraction template; no compiled translation catalogs are
shipped yet. Add `.po` catalogs under `cs2blocker/locale/` before advertising
translated UI coverage.
